Custom display pages are the default OpenYida path for dashboards, portals, visual reports, calculators, and rich interactive pages. OpenYida compiles modern React function components into Yida-ready pages and publishes them to the target page container.

## End-to-end flow

```bash
openyida agent-capabilities --summary-json
openyida create-page <appType> "Dashboard"
# Generate or author page source: project/pages/src/dashboard.canvas.jsx
openyida publish project/pages/src/dashboard.canvas.jsx <appType> <formUuid>
```

Use `agent-capabilities` to confirm the current environment, login state, and available capabilities. `create-page` returns the page `formUuid`; do not invent this value. Save it in your project cache or read it from command output. Once the page source is ready, use `publish` to update the target page. Publishing runs the required modern-page compilation and writes the page content.

## Page rules

New custom pages should use the modern page path. Generated page source should follow these rules:

- Use React function components for the page entry.
- Hooks such as `useState`, `useEffect`, and `useMemo` are supported; clean up side effects.
- Import UI libraries, chart libraries, and icons from the supported resource list.
- Buttons, filters, search fields, tabs, pagination, and clickable cards must drive real interaction.
- Prefer real data through the Yida data bridge, connectors, or Open APIs; provide empty, error, and refresh states.
- Use component tokens, CSS variables, and page-level styles as needed, with a readable mobile layout.

## Supported native Yida components

Custom pages can bridge native Yida runtime components. Detect components from `window.Deep`, `window.DeepYida`, or `window.YidaNativeComponents` first; if detection fails, render a page-owned fallback so the page does not go blank.

| Component / scenario | Best for | Integration requirement |
| --- | --- | --- |
| `PortalTopBanner` / `PortalQuickEntry` | Portal banner and quick entries | Prefer them for portal shells; fall back to page-owned banner and entry cards. |
| `QuickAccessCard` / `RecentlyUsedCard` | Frequent and recently used app cards | Pass `theme`, such as `row-white` or `column`, and keep local fallback. |
| `DataManageViews` | Embedded Yida data-management view | Pass the target form `form.appType` and `form.value` / `formUuid`. |
| `EmployeeField` | Member picker | Record the real `onChange` output first, then normalize member values. |
| `DepartmentSelectField` | Department picker | Verify search, popover, permission prompts, single select, and multi select. |
| `AttachmentField` / `ImageField` | Attachment and image upload | Verify upload permission, OSS signature, preview, delete, and failure states. |
| `DataCard` / `PortalContainer` | Portal data-card and container enhancement | Use only after the target portal context, data config, and style variables are verified. |

Native components are experience enhancements, not prerequisites for page stability. Keep fallback usable and normalize members, departments, and files before submitting.

## Publish and confirm

```bash
openyida publish project/pages/src/dashboard.canvas.jsx <appType> <formUuid>
```

Before publishing, confirm the source includes real interactions, mobile responsiveness, empty/error states, and the required data access logic. `publish` is the online update command and publishes the current source to the target page returned by `create-page`.

## Hide Yida navigation

Use this for full-screen dashboards or presentation pages:

```bash
openyida update-form-config <appType> <formUuid> false "Dashboard"
```

To show navigation again:

```bash
openyida update-form-config <appType> <formUuid> true "Dashboard"
```

## When to use `build-page`

```bash
openyida build-page project/pages/src/dashboard.canvas.jsx --write
```

`build-page` processes local page source without publishing. It is useful for review, CI, or debugging compile output.
